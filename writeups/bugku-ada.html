Misc 图片隐写 文件尾追加

Bugku 啊哒：文件末尾多出来的那段

2026-11-09 · 约 8 分钟 · Bugku CTF

图片能正常打开，但文件比预期大了一截。多出来的字节，就是别人不想让你看到的东西。

题目信息

平台Bugku CTF
类型Misc（图片隐写 / 文件结构）
知识点文件头识别、binwalk、JPEG 结束标记、数据分离
flagflag{...}

附件是一张 JPEG。打开完全正常，画面完整，没有任何异样。如果只看图，这题根本无从下手——所以第一步不是看图，而是看文件本身。

file 先说话

拿到任何未知文件，我的第一反应都是 file。它读的是文件头魔数，不看扩展名，所以能立刻告诉你「它到底是什么」。这一步看似简单，却能挡掉后面一大半弯路。

$ file ada.jpg
ada.jpg: JPEG image data, JFIF standard 1.01, resolution (DPI), 800x600

输出确认它是合法的 JPEG，宽 800、高 600。接着看大小：一张 800x600 的普通照片，压缩后一般几百 KB；如果 ls -l 显示它有 1.2 MB 甚至更大，那这个差值就很可疑了。

「是 JPEG」和「只有 JPEG」是两件事。前者说明文件头合法，后者才说明文件里没有别的东西。隐写题经常利用这个认知差：只要文件头合法、结束标记之前的内容完整，图片就能正常打开，而尾部追加的几百 KB 会被大多数解码器直接忽略。

binwalk 扫一遍

确认可疑之后，用 binwalk 扫一遍。它的原理是拿一堆已知的文件头签名在文件里做匹配，所以能找出「一个文件里藏了另一个文件」这种情况。

$ binwalk ada.jpg

DECIMAL       HEXADECIMAL     DESCRIPTION
--------------------------------------------------------------------------------
0             0x0             JPEG image data, JFIF standard 1.01
126976        0x1F000         Zip archive data, at least v2.0 to extract

结果一目了然：偏移 0 是 JPEG，偏移 0x1F000 处出现了一个 Zip 压缩包。也就是说，图片的数据在 0x1F000 之前就结束了，后面挂着一个完整的 zip。

要注意 binwalk 给出的偏移只是「疑似」，因为它靠签名匹配，偶尔会有误报。验证方法很简单：用 dd 把那一段切出来，再用 file 看一次。

dd if=ada.jpg of=tail.zip bs=1 skip=126976
file tail.zip

看文件尾：FF D9 之后还有什么

JPEG 的结束标记是 FF D9。一个正常的 JPEG，最后两个字节就该是它；如果 FF D9 后面还有内容，那些内容就是纯粹的追加数据，和图片本身没有关系。

用十六进制工具翻到文件末尾，或者用脚本找最后一个 FF D9 的位置，都能立刻看出端倪：

data = open('ada.jpg', 'rb').read()

end = data.rfind(b'\xff\xd9')       # 最后一个 FF D9
print('结束标记偏移:', hex(end))
print('文件总长度:', hex(len(data)))
print('尾部多余字节:', len(data) - end - 2)

如果「尾部多余字节」是一个很大的数，那基本可以确认追加了东西。这时再结合 binwalk 给出的偏移，两边一对照，位置就锁定了。两个独立方法互相验证，比只信一个工具踏实得多。

分离与提取

最简单的方式是让 binwalk 自己解：binwalk -e ada.jpg，它会把识别到的嵌套文件按偏移切出来，放到一个下划线开头的目录里。foremost 也可以，它按签名做 carving，对图片里嵌压缩包这种情况很稳。

binwalk -e ada.jpg
foremost -i ada.jpg -o out/
ls out/

分离出来的东西可能是 zip，也可能是一段 base64 文本、一个二维码图片。如果是 zip 且提示需要密码，先别急着爆破，看一眼是不是「伪加密」：zip 的通用标志位里有一个 bit 表示「该条目已加密」，把它清零往往就能直接解压。这类小技巧在 Misc 里出现频率很高。

解压之后通常就能拿到 flag。如果解出来的是文本，而文本又像某种编码，那就回到编码题的老路：一次剥一层，每层都看一眼输出是否可读。

踩坑与复盘

  • 一开始只看图，没看文件，白白浪费了十几分钟。
  • 用 tail -c 200 看末尾，结果看到的是 zip 的压缩数据，二进制乱码，误以为没有东西。
  • 直接改扩展名为 .zip 解压失败——因为 zip 不在文件开头，必须有偏移。
  • binwalk 的版本不同，输出格式略有差异，别死记某一行的样子。

复盘下来，这题的核心不是某个工具，而是「文件完整性」这个假设。我们默认「一张图就是一个图片文件」，所以从没想过它后面还能挂东西；但文件格式只规定了「哪里开始、哪里结束」，并没有规定「结束之后不能再写字节」。追加数据破坏了前者之外的约定，却完全不破坏「能打开」这件事。

引申：为什么追加数据不会把文件弄坏

大多数图片格式（JPEG、PNG、GIF）的解码器都是「读到结束标记就停」，后面的字节既不校验也不渲染。所以往一张图后面追加任意内容，图片照样能打开，只是文件变大了一点。这个特性被大量用于隐写，也被用于「把压缩包伪装成图片」这种绕过上传检测的手法。

防守方的思路也就清楚了：不能只看文件头魔数，还要校验文件长度是否与结构自洽，必要时做二次解码（把图片重新编码一遍），把尾部多余数据直接丢掉。对 CTF 来说，这个知识点叫「文件尾追加」；对真实场景来说，它叫「文件类型检测不能只信魔数」。
