Web X-Forwarded-For HTTP头伪造

Bugku 管理员系统：伪造一个来源 IP

2026-10-16 · 约 8 分钟 · Bugku CTF

页面说「只允许管理员从内网访问」。既然它信 HTTP 头，那我就可以是内网，也可以是管理员。

题目信息

平台Bugku CTF · Web
类型来源 IP 校验绕过
知识点X-Forwarded-For、X-Real-IP、信任边界
目标进入只对「本地 / 内网」开放的管理页

页面上的两个提示

首页只有两句话：一句是「只允许管理员访问」，另一句是「只允许本地访问」。我先是老老实实找登录口、翻 robots.txt、看 JS 里有没有藏接口，折腾半天没有进展。 后来把请求丢进 Burp 重放，随手加了一个 X-Forwarded-For: 127.0.0.1，页面直接变成了管理界面。

那一刻有点无语 —— 不是我技术变强了，而是它把「我是谁」完全交给了我的请求头。这类题考的不是漏洞深度，而是对 HTTP 信任模型的理解。

为什么这种校验是假的

X-Forwarded-For 不是 HTTP 标准里的头，它是一串由代理「顺手加上」的约定。客户端完全可以自己写一个发出去，服务器看到的值和真实连接毫无关系。 更糟的是，如果服务器直接拿 $_SERVER['REMOTE_ADDR'] 之外的头做判断，就等于让攻击者自己声明身份。 

<?php
// 典型的错误写法：拿一个可伪造的头当"内网身份"
$ip = $_SERVER['HTTP_X_FORWARDED_FOR'] ?? $_SERVER['REMOTE_ADDR'];
if (strpos($ip, '127.0.0.1') !== false || strpos($ip, '192.168.') === 0) {
    echo "welcome, admin: flag{...}";
} else {
    echo "only local admin";
}

这个判断有两个致命点。第一，它信了客户端能写的头；第二，它用 strpos 做「包含」匹配，127.0.0.1.attacker.com 这种值也能过。 正确的做法只能是：判断代理链、由最外层可信代理覆盖该头，而不是在应用层「读一下头就放行」。

还有个常见误区：REMOTE_ADDR 是 TCP 连接对端的地址，前面没有代理时它伪造不了；可一旦加了 Nginx，REMOTE_ADDR 就变成 Nginx 自己， 代码只好去看 XFF —— 问题恰恰出在「只好」这两个字上。

用 Burp 或 Hackbar 加一个头

方法很多：浏览器插件（Hackbar、ModHeader）加自定义头最省事，批量试就上 Burp 的 Repeater，纯命令行走 curl -H。我习惯先用 curl 确认，因为结果能贴进笔记复现。 

# 最直接的：声明自己是本机
curl -H "X-Forwarded-For: 127.0.0.1" "http://靶机/admin.php"

# 有的实现只认 X-Real-IP 或 Client-IP
curl -H "X-Real-IP: 127.0.0.1" "http://靶机/admin.php"

# 代理链写法：逗号分隔，最左边是"客户端"
curl -H "X-Forwarded-For: 127.0.0.1, 10.0.0.1" "http://靶机/admin.php"

X-Forwarded-For 的语义是「谁经过了谁」：最左边是原始客户端，往右是各级代理。很多代码取第一个值，也有很多取最后一个， 所以有时两种顺序都要试。日志里看到一个陌生的 IP 排在前面，并不代表它真的连过服务器。

如果还不行：补上身份线索

有些题除了 IP 还校验 User-Agent 或 Referer。这种情况下单加 XFF 没反应，得把整套身份补齐；先把响应头和报错读干净，它会告诉你缺什么：

  • 提示「必须是管理员」→ 试 User-Agent 里带 admin 字样，或加 Cookie: role=admin。
  • 提示「只能从内网访问」→ 优先试 X-Forwarded-For，其次 X-Real-IP、Client-IP、Forwarded。
  • 提示「请从管理后台跳转」→ 补 Referer: http://127.0.0.1/admin/，这类校验同样不可信。

Forwarded 是标准化的替代头，格式是 for=127.0.0.1;proto=http。开发时新旧两套都兼容的代码很多，所以两个都值得试。

真实环境里为什么不能这么写

生产环境的链路通常是「客户端 → CDN/WAF → Nginx → 应用」。如果应用直接信任 XFF，那么任何人只要绕过前三层直连源站，或者前三层只是「追加」而不是「覆盖」， 就能把自己写成任何 IP。真正安全的前提是：应用只信任来自已知代理网段的连接，并且由最外层代理把客户端自带的 XFF 丢弃、重新生成一条干净的链。

换句话说，IP 是网络层身份，不该由应用层从请求头里读。应用该让代理传递签名过的身份（JWT 或 mTLS），而不是一个随便填的字符串。

还有一种更隐蔽的情况：WAF 把 XFF 清洗干净了，应用却自己又拼了一遍「客户端值, 代理 IP」，第一个值仍然是攻击者写的。 清洗必须发生在最外层，而且用完就覆盖，不能留在链中间。

防御建议

  • 不要在应用代码里用 HTTP_X_FORWARDED_FOR 判断权限；权限判断应该基于会话和角色。
  • 如果一定要取真实 IP，只采信「来自已配置代理网段」的请求，并从代理链的右侧往回取，而不是取第一个。
  • 在 Nginx 层用 real_ip_header + set_real_ip_from 限定可信来源，并显式覆盖客户端传入的值。
  • 管理后台不要靠「内网 IP」当唯一门槛，改走 VPN、SSO 或多因素认证。
  • 用严格匹配或 ip2long 网段判断，别用 strpos 这种包含匹配。
