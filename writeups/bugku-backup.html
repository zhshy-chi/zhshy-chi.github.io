Bugku 备份是个好习惯：把 .bak 翻出来

2026-10-10 · 约 8 分钟 · Bugku

站长备份文件时忘了删，整份源码就躺在 web 目录里等人下载。这篇记一下常见备份命名、怎么扫出它们，以及拿到源码之后该看哪里。

题目信息

平台Bugku CTF 练习平台
类型Web / 源码泄露
知识点备份文件命名、目录扫描、PHP 源码审计
工具dirsearch、御剑、curl

页面长什么样

首页非常朴素，一段欢迎文字加一个查 flag 的输入框。随便填点什么提交，页面只回一句「没有找到」。源码里没有注释，也没有多余的外链，看不出任何可利用的点，像是故意做得干干净净。

但题目名字已经把方向写死了：「备份是个好习惯」。这句话不是让你养成备份习惯，而是在告诉你 —— 这里有人备份过，而且备份放在了一个能被访问到的地方。那就别在功能上纠缠了，去翻文件。

常见的备份命名

备份文件泄露之所以好挖，是因为命名高度规律。手工维护的备份通常是「原名加后缀」：index.php.bak、index.php~、index.php.swp、index.php.save、index.php.old、.index.php.swp。打包备份则常叫 www.zip、www.tar.gz、web.rar、backup.zip、站点名.zip。

还有一类是版本控制目录被一起传上去：.git/、.svn/、.hg/。它们比单个备份更危险，因为整个仓库的历史都在里面，哪怕当前源码删掉了敏感逻辑，翻历史提交也能找回来。

目录扫描找备份

手猜几个最常见的先试：/index.php.bak、/www.zip、/.git/HEAD。前两个都 404，但 /.git/HEAD 返回了 ref: refs/heads/master —— 说明 .git 目录是公开的。这条线索比单个备份更值钱。

拿工具扫一遍更省事，dirsearch 一条命令： 

python dirsearch.py -u "http://靶机地址/" -e bak,zip,tar,gz,old,swp -w backup.txt

御剑也行，字典选「备份文件」那一类。扫描的时候注意看响应长度：备份文件往往比 404 页面大，长度一列会明显跳出来。如果站点有 WAF，把线程数降到 1，加个延迟，别把目标打挂。

下载并审计源码

.git 泄露可以用 GitHack 或者 dirsearch 配合工具把仓库还原出来。还原之后 git log 翻一遍，最后一次提交的说明里常常写着「fix bug」或者「remove test」，正好指向你要找的那段逻辑。 

python GitHack.py "http://靶机地址/.git/"
cd 靶机地址
git log --oneline --all

翻到一个 flag.php，内容大致是： 

<?php
$key = $_GET['key'];
if (md5($key) == '0e123456789012345678901234567890') {
    echo 'flag{...}';
} else {
    echo '没有找到';
}
?>

这段代码用 md5 的返回值和一个 0e 开头的字符串做松散比较。乍看是拿哈希当密码，好像很安全，问题其实出在 == 上：0e 后面全是数字的字符串会被当成科学计数法，两边都转成 0，于是相等。也就是说，只要找一个 md5 之后形如 0e123... 的字符串，就能白嫖这一关。审计时把每个比较符是 == 还是 === 标出来，这类点一眼就能看见。

从源码里读出绕过条件

继续往下翻，还有一层判断：if ($key == 'admin')，但前面又 if (is_numeric($key)) die()。两个条件叠加，还是老配方 —— 要一个「不是数字却等于 admin」的值，PHP 5 里 admin 转数字是 0，所以 $key 传 0 反而会被第一关拦下。真正的解法在另一个分支：strcmp($key, $flag)，传数组进去让它返回 null，null == 0 成立，直接过。

这段审计过程比 payload 本身重要。拿到源码之后不要急着搜 flag，先通读一遍数据流：参数从哪进来、经过了哪些判断、最后在哪被使用。判断和使用的函数不一致，就是绕过点；判断漏了某个类型（数组、对象），就是绕过点。

拿到结果

按源码里的条件构造请求，页面回显 flag{...}。整个过程没有爆破、没有复杂利用，纯粹是「看到了不该看到的文件」。这也是源码泄露类题目的共同特征：拿到源码的一刻，题就做完了一半。

信息收集阶段多花十分钟翻备份，可能比后面花两小时猜逻辑更有效。攻击面不只在功能里，也在没人维护的角落里。

踩坑与复盘

  • 一开始只在输入框里试各种注入，完全没往文件方向想，浪费了不少时间。
  • 一开始手工猜 index.php.bak 和 www.zip 都是 404，以为没戏，差点去研究那个输入框；换成 /.git/HEAD 才发现真入口。
  • 审计时没注意 == 和 === 的区别，按强比较的思路构造了半天，回头细看源码才发现是松散比较。

防御建议

最直接的一条：永远不要把备份、压缩包、版本控制目录放进 web 根目录。备份统一放到站点之外的位置，文件名加随机串，定期清理。nginx 里显式 deny 掉 \.(bak|old|swp|zip|tar|gz)$ 和 /\.git/，Apache 用 <FilesMatch> 配同样的规则。CI 流水线里加一步检查，发布前把这类文件挡在门外，比出事之后再删要靠谱得多。
