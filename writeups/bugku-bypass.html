Bugku 各种绕过：一次试完所有花招

2026-10-18 · 约 9 分钟 · Bugku CTF

这题关键词过滤得很凶，但过滤规则永远写不全 —— 把能试的编码都试一遍，是我这次最大的收获。

题目信息

平台Bugku CTF · Web
类型黑名单过滤绕过
知识点空格替换、关键字变形、URL 编码、数组传参
目标让被拦的 payload 通过校验并执行

先探清楚它到底拦什么

别一上来就跑字典。我的顺序是：先交一个普通字符串，看回显有没有变化；再交单个特殊字符（'、"、;、空格、/、<）， 看它是「删掉」「替换成空」还是「直接报错」。三种反应对应三种绕过方式。

这题我探出来的结果很典型：空格被过滤，select、union、system 被拦，但过滤方式是「替换为空」而不是「终止请求」。 后者可以放弃，前者意味着只要变形到「替换后仍能还原语义」，就能过。

第一板斧：空格与关键字

空格被吃掉时，SQL 里最稳的替代是注释 /**/，命令行里是 ${IFS}，URL 里还有 %09（Tab）、%0a（换行）、+。 它们在不同解析层的效果不一样，所以我会一次列出来挨个试： 

# 空格被过滤后的常见替代
union/**/select/**/1,2,3
union%09select%091,2,3
union%0aselect%0a1,2,3
cat${IFS}/flag

关键字被拦时，先试大小写（SeLeCt），再试双写（selselectect）—— 有些过滤只替换一次，替换后拼起来正好是原词。 中缀注释也常有效：sel/**/ect。这三个方向几乎覆盖了「只做字符串替换」的过滤。

第二板斧：URL 编码与二次编码

这是最容易被忽略的一层。WAF 和业务代码看到的往往不是同一份字符串：WAF 在 urldecode 一层之后匹配，而框架可能再解码一次。 于是把 ' 写成 %2527，WAF 解一次得到 %27（不像引号），应用再解一次才变回 '。 

# 单引号的层层变形
'            → 直接被拦
%27          → 解一次就是 '，通常也拦
%2527        → 解一次是 %27，解两次才是 '
%u0027       → IIS 老解析器的 unicode 写法

实操时我会在 Burp 里勾上「URL-encode as you type」，或者直接改 Repeater 的原始报文 —— 浏览器和工具会自动编码， 有时我以为发出去的是 %2527，其实早被编码成 %252527，试半天都是自己骗自己。

第三板斧：用数组把参数变成 Array

如果后端用 strpos、preg_match 这类函数做检查，传数组会让它们直接失效：strpos(array, 'x') 在 PHP 8 会抛 TypeError， PHP 7 返回 null 并警告；preg_match 遇到数组同样返回 false。 如果代码写的是「匹配到就 die」，那返回 false 反而等于「没匹配到」，检查被跳过。 

<?php
// 传 a[]=1 时，strpos 收到的不是字符串
if (strpos($_GET['a'], 'flag') !== false) {
    die('hacker');
}
echo file_get_contents($_GET['a']);   // 检查被跳过，直接读

这就是「过滤」和「校验」的区别：过滤假设输入是字符串，而 PHP 的参数天生可以是数组。只要代码没做 is_string 判断，类型就能成为绕过点。

还有一层常被忽略：长度。有的 WAF 只匹配前 N 个字节，payload 一长就被截断；这时把关键部分往后挪、或者用注释填充，反而能过。 规则写得越具体，可利用的边角就越多。

payload 对照表

被拦的东西替换写法为什么有效
空格/**/、%09、%0a、${IFS}不同解析层都认这些分隔符
关键字SeLeCt、selselectect、sel/**/ect替换只做一次，或匹配区分大小写
引号 / 尖括号%2527、%253C多层解码，WAF 与应用看到的不是同一串
参数类型?a[]=xstrpos / preg_match 遇数组返回 false
长度限制分段传参、chr() 拼接绕开「一次请求只能多长」的假设

用这张表的方式是「一次只改一个变量」：先固定其它部分，只替换空格，看响应有没有变化；再替换关键字。 同时改三处，成功了不知道是哪一处起作用，失败了更不知道该往哪调。另一个细节是分清两种拒绝：被 WAF 拦通常是 403 或固定的拦截页， 被业务代码拦是自己写的提示语，把「业务报错」当成「绕过成功」是我早期最爱犯的错。

为什么黑名单注定会漏

黑名单的本质是「列举所有坏东西」，而语言的表达方式无穷无尽：编码、大小写、注释、类型转换、等价函数（system 换成 passthru、exec、反引号）。 防守方永远在补，攻击方找到一个没被列举的等价写法就赢了。

这题让我记住一句话：过滤是「减去危险」，校验是「只留下安全」。前者必然有漏，后者才可穷举。

防御建议

  • 用白名单而非黑名单：参数只接受明确允许的字符集和长度。
  • SQL 一律参数化查询，不要靠转义和关键字过滤兜底。
  • 命令执行用参数数组形式（proc_open 的数组参数），不要拼字符串。
  • 入口统一做类型校验（is_string / filter_var），别让数组流进字符串函数。
