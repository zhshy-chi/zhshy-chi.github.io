Web HTTP响应头 Burp

Bugku 头等舱：答案在响应头里，不在页面上

2026-10-05 · 约 6 分钟 · Bugku

页面干干净净什么都没有。但 HTTP 响应不只有 body，还有一堆 header —— 这道题考的就是「你会不会把响应看全」。

题目信息

平台Bugku CTF 练习平台
类型Web / 信息收集
知识点HTTP 响应头、Burp Suite、base64 识别
工具浏览器 F12、Burp、curl

页面：干干净净，什么都没有

打开题目地址，浏览器渲染出一张白页。右键看源码，只有一层 html、head、body 的骨架，body 里空着，没有注释、没有隐藏元素、没有外链脚本。这种页面第一反应会以为题挂了，或者地址错了。

但只要记住一件事：浏览器展示的只是响应体（body）。一个 HTTP 响应由状态行、响应头和响应体三部分组成，body 为空，不代表这次响应没有内容。名字叫「头等舱」，其实已经把提示写在标题里了 —— 答案在头里。

顺便说一句，找隐藏信息不要只盯着正文。注释、隐藏的 div、被注释掉的 JS、Cookie 里的字段，都是常放提示的地方。这道题在源码里什么都没留，反而更说明信息不在页面上，得往传输层看。

先看源码，再看完整响应

我习惯的顺序是先源码、再 Network、最后上 Burp。源码确认没有东西之后，按 F12 打开开发者工具，切到 Network 面板，刷新一次页面，点开那条文档请求，右边会分成 Headers、Preview、Response 几个标签。Headers 里又分 Response Headers 和 Request Headers 两块，flag 一般在前者。如果觉得开发者工具的展示太零碎，可以在 Burp 的 Proxy → HTTP history 里选中这条请求，右边 Response 切到 Raw 视图，完整的响应原文一行不少，比 F12 更适合逐条核对。

用命令行更快，curl -I 只取响应头，不下载 body： 

curl -I "http://靶机地址/"

如果站点是 HTTPS 或者需要带 Cookie，就换成 curl -isk，把请求头和响应头都打出来。-i 表示把 header 一起输出，-s 安静模式，-k 忽略证书问题。这三种参数组合在信息收集阶段非常常用。要注意 -I 发出去的是 HEAD 请求，少数服务端对 HEAD 和 GET 返回的头并不一致，如果结果为空或者看着可疑，就换 curl -i 用 GET 再确认一次。

逐条读响应头

拿到的响应头大概是这样，一条条看下来： 

HTTP/1.1 200 OK
Server: nginx/1.18.0
Date: Thu, 01 Oct 2026 03:12:44 GMT
Content-Type: text/html; charset=utf-8
Content-Length: 0
X-Powered-By: PHP/7.4.3
X-Backend-Server: web-node-02
Set-Cookie: session=eyJ1aWQiOjF9; path=/
X-Flag: ZmxhZ3suLi59
Vary: Accept-Encoding

Server 和 X-Powered-By 暴露了 nginx 版本和 PHP 版本，这本身就算信息泄露，能帮攻击者缩小选 payload 的范围。X-Backend-Server 是自定义头，说明前面有代理或者负载均衡，后端节点名也一并漏了出来。Set-Cookie 里那个值是 base64，解开是 {"uid":1}，属于会话信息，虽然本题用不上，但值得留意。

真正可疑的是 X-Flag。正常业务不会起这种名字，值又长得像 base64：长度是 4 的倍数，字符集只含大小写字母和数字，末尾还没有等号填充。看到这种特征，先解码再说。

找到可疑的头并解码

解码一行命令就够： 

echo "ZmxhZ3suLi59" | base64 -d

输出是 flag{...}，题目要求的格式对上了。如果解出来是乱码，大概率不是 base64 而是十六进制或者 URL 编码，可以按 %、\x 之类的特征换工具；也有题目会套两层，先 base64 再 URL 解码。判断编码类型没有捷径，多看字符集和长度，试两次就有手感了。

另外别只盯着自定义头。响应头里偶尔会藏 X-Forwarded-For、Via、X-Cache 这类代理留下的痕迹，或者把提示塞进 Set-Cookie 的注释里。如果首页干净得可疑，还可以把同样的方法套到 /index.php、/admin、/flag.php 这些路径上，有的题只在某个特定路由的响应里加了头。养成「把整个响应从头读到尾」的习惯，比记住某个头名有用。

页面是给人看的，响应是给机器看的。人看到空白，机器看到一整个头部 —— 信息收集的第一步，永远是拿到完整响应。

踩坑与复盘

  • 先在源码里翻了三遍注释，又去试了 /robots.txt、/flag.php，全是 404，白白浪费了时间。
  • 用 F12 时一开始只看了 Preview，忽略了 Headers 标签，后来才想起来响应头在另一个页签。
  • base64 解出来后没敢确认，又拿 Burp 的 Decoder 交叉验证了一遍，确认不是别的编码。

防御建议

生产环境应该关掉 X-Powered-By 这类版本头，把 Server 的详细版本号抹掉，自定义头里不要放任何业务数据、内部节点名或调试信息。代理层同样要清理会泄露内网结构的头。信息泄露单看每一条都不严重，但拼起来就是一张给攻击者的地图。
