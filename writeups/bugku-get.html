Bugku web 基础 GET：把参数写进 URL

2026-09-24 · 约 6 分钟 · Bugku 练习场

源码里写着 if($what=='flag')，那我要做的只是让 what 等于 flag。

题目信息

平台Bugku 练习场
类型Web · GET 传参
知识点query string、$_GET、curl 复现请求

这是 Bugku Web 基础里的 GET 题，题面直接把源码给了，几乎是送分。但它值得写一篇，因为「参数在 URL 上」这件事是后面所有 Web 题的起点。

题面给的代码

这题很大方，源码直接贴出来了：

<?php
$what = $_GET['what'];
echo $what;
if ($what == 'flag') {
    echo 'flag{...}';
}
?>

逻辑干净：从 GET 里取 what，原样回显，然后判断是否等于字符串 flag，相等就输出 flag。没有过滤，没有绕弯，也不需要绕弯——题目要的就是「把参数传成 flag」。

从代码到请求：参数到底在哪

$_GET 是 PHP 里取 URL 查询字符串的数组。浏览器请求 http://靶机/?what=abc，问号后面那一段叫 query string，服务器会把它按 & 和 = 拆开，塞进 $_GET。所以 what=flag 就是在告诉 PHP：$_GET['what'] 的值是 flag。

有个容易忽略的点：问号后面的内容属于 URL 的一部分，不属于页面内容。页面上没有任何输入框，也没有表单，参数完全由访问者自己拼。源码里的 echo $what 会把传进去的值打印出来，这本身就是个回显点——先传个 hello 看它是不是真的回显，再传 flag，是很自然的验证顺序。

另外要习惯 URL 编码：中文、空格、& 这类字符在 query string 里都有特殊含义，浏览器会自动把它们编码成 %XX。手工拼参数时如果值里带 &，得写成 %26，否则服务器会把它当成两个参数的分隔符。

调试习惯：不确定参数名是 what 还是 w 的时候，先随手传一个能区分的值，看页面回显什么。回显是最直接的反馈，比猜快得多。

地址栏和 curl 两条路

第一条是地址栏：直接访问 http://靶机/?what=flag，回车。浏览器把这一整串当成请求行里的路径发给服务器，PHP 解析出 what=flag，条件成立，flag 就出现在页面上。整道题不到十秒。

第二条是命令行，用 curl 复现同一条请求。它和地址栏发的是同一个 HTTP 请求，只是少了浏览器的渲染：

curl -s "http://靶机地址/?what=flag"
curl -s -i "http://靶机地址/?what=flag"        # 顺便看响应头
curl -sv "http://靶机地址/?what=flag" 2>&1 | head -n 20

加 -v 能看到完整的请求行，那行长这样：GET /?what=flag HTTP/1.1。GET 的参数全部在请求行的 URL 里，后面没有请求体。这也是为什么这题用浏览器就够了，连抓包都不用。

GET 和 POST 到底差在哪

最朴素的区别是参数放哪：GET 放在 URL 的 query string 里，POST 放在请求体里。由此衍生出一串实际差异。

GET 的 URL 会进浏览器历史、会被代理和服务器访问日志记下来、会出现在 Referer 里；POST 的 body 一般不进这些地方，但明文 HTTP 下的 body 照样能被中间人看到。GET 在协议层面没有长度限制，「GET 有长度限制」这个说法并不严谨——限制来自浏览器和服务器实现，比如某些服务器默认只接受 8KB 的请求行，工程上确实不该用 GET 传长内容，但那是实现约束，不是协议规定。

还有语义上的区别：GET 应该是幂等的、只读的，POST 才用来改状态。这条是约定而非强制，但它解释了为什么搜索引擎只爬 GET、为什么刷新一个 POST 页面浏览器要问你要不要重新提交表单。

为什么「能改 URL 就等于能改参数」

服务器判断逻辑时，看的是请求里带过来的值，而请求是客户端构造的。URL 是客户端能完全控制的部分，所以 query string 里的任何东西都不能当可信输入。

一个常见的错误写法是只在页面上把入口藏起来，或者用 JS 判断「这个用户不该看到这个链接」，但接口本身不校验。攻击者不需要你的按钮，他只要手写 URL。这题把这条道理压缩成了三行 PHP，代价很小，印象很深。

这也是为什么很多真实漏洞的入口看起来「不可能点到」——链接藏在 JS 里、按钮是 hidden、接口文档没公开，但只要路径和参数猜得到，这些「藏」都不算防护。真正的防护只有一种：服务端在每次请求里重新判断一遍。

防御上：参数一律在服务端校验，尤其身份和权限相关的值；不要把「前端没显示入口」当成访问控制；回显的内容做 HTML 转义，避免顺手送出一个 XSS。这题里的 echo $what 就是典型例子——它能回显 flag，也能回显一段脚本。
