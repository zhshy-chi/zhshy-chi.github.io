Bugku 计算器：maxlength 挡不住任何人

2026-09-22 · 约 6 分钟 · Bugku 练习场

让输入一个加法结果，但输入框死活只能打一位数。这不是题目难，是前端在拦你。

题目信息

平台Bugku 练习场
类型Web · 前端
知识点maxlength 属性、修改 DOM、客户端校验不可信

这题在 Bugku 里叫「计算器」，是很多人做 Web 的第一道题。知识点不深，但它第一次把「前端」和「后端」的边界摆到了你面前。

现象：输入框只吃一位数

题目给两个数相加，答案是个三位数。我第一次输入时只打进去一位，后面再按键盘就没反应了，输入框像被焊住一样。删掉重打，还是一样。页面不报错，也不提示「最多一位」，它就是安安静静地不接收。

这种「没有报错但就是不让你输入」的表现，八成是属性限制，不是逻辑判断。逻辑判断通常会给你一句提示，而 maxlength、readonly、disabled、pattern 这些 HTML 属性是浏览器在输入层面直接拦掉的，连提交的机会都不给。分清这两种情况，排查方向就完全不同。

F12 里那个 maxlength="1"

按 F12 打开 Elements，选中输入框，右侧属性列表里有一行 maxlength="1"。就这么简单。

maxlength 是 HTML 原生属性，作用是限制用户能输入的最大字符数，由浏览器执行。它跟服务端没有任何通信——服务器根本不知道你的输入框上写了这个属性，它只是收到了一个被浏览器截断的字符串。

找到之后有三种改法：双击属性值，把 1 改成 10；或者右键选 Edit as HTML，把整个属性删掉；再或者用控制台一行搞定。三种方式效果一样，都是改当前页面内存里的 DOM。

# 原始 HTML 大概长这样（这里的尖括号已转义）
<input type="text" name="sum" maxlength="1">

# 控制台里直接改属性
document.querySelector('input[name=sum]').maxLength = 10

# 或者干脆把整个 input 重建成不带限制的
document.querySelector('input[name=sum]').removeAttribute('maxlength')

改掉属性，再把正确结果提交

改完立刻输入完整的三位数，点提交。这次表单带着完整答案发出去，页面返回了 flag{...}。

值得记一笔：DOM 的修改只存在于当前这个标签页里，刷新就恢复原样，因为原始 HTML 是服务器发过来的，你改的只是浏览器里的一份副本。这不影响做题——我只需要让这一次请求带上正确的值，服务器验证的是请求里的参数，不是我屏幕上显示的输入框。

换句话说，就算懒得改页面，也可以直接构造请求。既然服务器只认参数，那它根本不在乎参数是从哪个输入框来的：

curl -s -i -X POST -d "sum=123" http://靶机地址/

改完 DOM 不要刷新，一刷新属性就回来了。另外，如果题目用 JS 在提交时再做一次校验，那改属性可能不够，得看它的校验函数——不过那是另一类题了。

为什么前端校验不算校验

这题的答案不在「怎么把数字打进去」，而在「为什么打不进去还能做对」。前端校验的本质是：校验代码运行在用户的机器上，而用户的机器归用户管。

浏览器拿到的是 HTML、CSS、JS 三样东西，它们全都能在本地被修改、被跳过、被替换。所以任何只在前端做的检查——长度、格式、必填，甚至「这个按钮是灰的不能点」——都只是体验优化，不是安全边界。

举个同类的例子：有些页面用 disabled 属性禁掉提交按钮，看着点不了，删掉属性就能点；有些用 JS 判断「必须是会员才能提交」，改个变量就过了。真正要挡人的判断必须发生在服务端，因为那里的代码和数据库不在攻击者手上。这题把这条结论压缩成了「改一个 maxlength」这么小的一件事。

复盘与防御

复盘一条：看到「输入被限制」，先分清是逻辑限制还是属性限制。逻辑限制会有提示、会有请求；属性限制悄无声息，改一下就好。判断依据是「有没有报错文案」和「Network 里有没有发出请求」。

防御侧：maxlength 留着对普通用户是好事，能减少误输入，但它替代不了服务端校验。服务端拿到参数后必须重新检查类型、范围、长度，哪怕前端已经查过一遍。前端校验是给人用的，服务端校验是给攻击者准备的——这句话我在这题之后就一直记着了。
