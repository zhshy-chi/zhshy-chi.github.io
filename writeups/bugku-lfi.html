Bugku 本地包含：include 后面的坑

2026-10-14 · 约 9 分钟 · Bugku CTF

页面把文件名拼进 include，而我想要的东西，就在同一台机器上。这篇把「验证包含 → 读源码 → 找真正目标」这条线走一遍。

题目信息

平台Bugku CTF · Web
类型本地文件包含（LFI）
知识点include 路径拼接、php://filter、源码泄露
目标读到被 PHP 执行掉、页面上看不到的源码

题面：一个 file 参数

打开页面只有一个很空的模板，链接里带着 ?file=。随手把它改成 ?file=about，页面内容变了，说明这个参数真的被拿去加载文件了。 题目源码（大致）就是三行： 

<?php
$file = $_GET['file'] ?? 'home';
include($file);      // 没有 basename，没有白名单，没有 realpath

这就是最经典的 LFI 形态：用户输入直接当路径，include 会在 include_path 和当前脚本目录里找这个文件。它能去的地方，比我以为的多得多。

第一步：先证明包含真的生效

在打任何花活之前，我要先确认「读到的内容会回显」。Linux 靶机先读 /etc/passwd，Windows 靶机试 C:\Windows\win.ini。如果页面里出现了一串 root:x:0:0:root:/root:/bin/bash， 说明漏洞是实打实的，剩下的只是「读哪个文件」的问题。 

curl "http://靶机/?file=../../../../etc/passwd"
curl "http://靶机/?file=../../../../etc/passwd%00"      # 老 PHP 的截断，5.3.4 之后没了
curl "http://靶机/?file=C:/Windows/win.ini"

.. 多写几层没关系，Linux 走到 / 就停住；Windows 则要注意盘符和反斜杠。

第二步：php://filter 把源码捞出来

直接 ?file=index.php 是没用的：include 会把 index.php 当 PHP 代码执行，<?php ... ?> 里的东西全被解释掉了，我看到的还是渲染后的空模板。 想看源码，就得让 PHP 在「读取」阶段把内容变成不会被执行的东西 —— php://filter 就是干这个的。 

# 把 index.php 以 base64 输出，PHP 就不会去解析它
curl "http://靶机/?file=php://filter/convert.base64-encode/resource=index.php"

# 解出来
echo "PD9waHAgJGYgPSAkX0dFVFsnZmlsZSddOyA..." | base64 -d

为什么一定要 base64？因为 php://filter 是流包装器，数据在进入 include 之前就已经被转码成纯文本了。 如果只写 resource=index.php，拿到的还是原始 PHP 代码，照样被当代码执行；而 base64 之后整段是一个「不像 PHP 的字符串」， include 找不到 <?php 标签，就当成普通文本原样输出。这是本题的核心。 过滤器还能用 | 串联，也有 convert.iconv 这类做编码转换的写法，绕 WAF 时更常用。

第三步：从源码里找真正的目标

源码拿到手，事情就好办了。我这次读出来的 index.php 里有这么一段：真正的 flag 不在当前目录，而是被另一个文件包含进来，路径和变量名都写在代码里。 比我瞎猜文件名靠谱多了： 

<?php
// 解码后看到的关键片段
$file = $_GET['file'] ?? 'home';
if (strpos($file, 'flag') !== false) {
    die('想得美');
}
include($file);

它只拦了 flag 这个子串，说明目标文件确实叫 flag 相关的名字。被拦了怎么办？php://filter 的 resource= 允许我再套一层路径， 也可以换成 php://filter/read=convert.base64-encode/resource=fl<something>ag.php 这种拼法，具体怎么绕取决于过滤强度。 我这里的做法是先枚举常见文件名（flag.php、config.php），确认后再读。

踩坑记录

  • 第一次直接 ?file=php://filter/resource=index.php，页面空白 —— 因为没加 convert.base64-encode，读到的 PHP 还是被执行了。
  • resource= 后面不要再写 php://，否则会变成 php://filter/.../resource=php://filter/...，报「无法打开流」。
  • Windows 靶机上 /etc/passwd 当然读不到，先换 win.ini 试试。
  • 解码时记得去掉 base64 前面的 HTML 杂讯，或者用 grep -o 截出那一段。

引申：LFI 到 RCE 的常见链条

只读文件只是 LFI 的上半场，真正的杀伤力在于 include 等于执行：只要能控制服务器上的某个文件内容，包含它就能执行代码。常见三种：

  • 日志包含：把 PHP 代码写进 User-Agent 或请求路径，让它落到 /var/log/apache2/access.log，再 include 这个日志。日志里有没有 <?php 被转义，决定了能不能成。
  • Session 文件包含：通过 session.upload_progress 或自己控制 session 值写入 /tmp/sess_<id>，再包含它。路径可预测，是很好用的一招。
  • 临时文件 / 伪协议：/proc/self/environ、上传临时文件配合竞争，都属于同一类思路。

所以要记住：LFI 的上限不是「能读多少文件」，而是「能不能读到可执行的内容」。一旦日志、session、上传目录可写且路径可猜，它就升级成 RCE。

顺便记一下另外两个伪协议：php://input 和 data:// 也能被 include，但它们要 allow_url_include=On， 默认是关的，所以大多数比赛题里走不通。真正通用的是 php://filter，因为它不需要任何开关。

防御建议

  • 不要把用户输入直接拼进 include；如果业务确实要动态加载，用白名单映射（['home' => 'pages/home.php']）。
  • 用 realpath() 求真实路径后，校验它是否仍在前缀目录内，防止 .. 和符号链接。
  • 关掉 allow_url_include，设置 open_basedir 限定可访问目录。
  • 日志、session 目录不要放在 Web 根下，也不要用可被包含的权限暴露。
