Bugku 点击一百万次：前端计数器的骗局

2026-10-03 · 约 6 分钟 · Bugku

让你点一百万次，显然不是真让你点。计数逻辑写在前端，就一定有办法跳过去 —— 问题只是找到那个真正参与判断的变量，而不是页面上显示的数字。

题目信息

平台Bugku CTF 练习平台
类型Web / 前端绕过
知识点JavaScript 变量、控制台调试、DOM 与状态分离
工具浏览器 F12

页面现象：一百万次的进度条

打开页面，正中一个按钮，下面一行文字写着「你已经点击了 0 次」，再往下是一条进度条。随便点几下，数字会加，进度条会动，手感上像是真的在计数。但按钮旁边还写了句「目标：1000000 次」。

这就是典型的「用体力替代思考」的题面。一百万次点击，就算手速再快也要按上几个小时，出题人显然不指望你真点。真正要问的是：这个数字存在哪里？它凭什么决定我能不能拿到 flag？

找到真正的计数变量

先看源码。页面没混淆，<script> 里能看到一个全局变量，大概叫 clicks，初值为 0，按钮的点击事件里做 clicks++，同时更新页面上那个 span 的文本。关键的一点是：这个变量的作用域在 window 上，控制台可以直接读写它。 

// F12 控制台里直接改全局变量
clicks = 999999

// 或者一步到位
clicks = 1000000

// 再点一下按钮，让它自己走完更新和提交逻辑
document.querySelector('button').click()

改完变量再点一次按钮，页面上的数字会直接跳到一百万，然后触发提交。这一步之所以成立，是因为计数、显示、提交这三件事共用同一个变量，只要把源头改掉，后面全都会跟着变。

直接调用它的提交函数

如果不想绕按钮，也可以顺着源码找提交函数。这类题一般会把「判断是否达标」和「发请求」写在一个函数里，比如 submit()、check()、postFlag() 之类。找到函数名之后，在控制台里直接调： 

// 先看看 window 上有哪些可疑函数
Object.keys(window).filter(k => typeof window[k] === 'function')

// 找到后直接调用，跳过点击
submit()

如果函数里带了判断（比如 if (clicks < 1000000) return;），先把 clicks 改大再调用，两招组合起来基本通杀。再退一步，还可以在 Sources 面板里给判断那一行下断点，命中的时候在 Scope 里手动改值，效果一样，只是更慢。

为什么改页面上的数字没用

这是这道题最容易踩的坑。新手的第一反应往往是在 Elements 面板里双击那个 0，改成 1000000，页面上确实显示一百万了 —— 然后点提交，什么也没发生。原因很简单：Elements 改的是 DOM 文本，而判断读的是 JavaScript 变量，两者只是被代码单向同步过，你把显示改掉，变量根本没动。

更麻烦的是，下一次点击事件触发时，代码会用变量的值重新渲染一遍 span，你改的数字当场被打回原形。所以判断一个「前端校验」能不能绕，先分清它读的是 DOM 还是内存里的状态：读 DOM 的，改 DOM 就够；读变量的，必须动变量。

提交与后端校验

数字凑够之后点提交，前端会把结果打包成一个请求发出去。抓包能看到大概长这样：POST /flag.php，body 里带一个 clicks=1000000 之类的字段。服务端拿到这个数字，只要大于等于阈值就把 flag 返回。

也就是说，整个「一百万次」的约束从头到尾都只是客户端的自觉，服务端并没有真的统计过点击次数 —— 它相信了浏览器报上来的数字。这意味着即使不改 JS，直接用 Burp 重放这个 POST，把 clicks 改成一百万，一样能过。两条路殊途同归，本质都是「约束没有落在服务端」。

判断一个校验值不值钱，只看一件事：把浏览器完全绕过、直接构造请求，它还拦不拦得住。拦不住，那它只是 UI 的一部分。

踩坑与复盘

  • 一开始在 Elements 里改了显示的数字，点提交毫无反应，卡了十分钟才想到看 JS。
  • 改完 clicks 后忘了再点一次按钮，页面没触发提交流程，以为方法不对；其实变量改了，但提交逻辑还没跑。
  • 后来发现直接重放 POST 更省事，也顺手验证了后端确实没有独立计数。

防御建议

任何「次数」「额度」「进度」类限制，都必须由服务端记录和判断，前端只负责展示。服务端要按会话或用户维度维护计数，并且对提交上来的值一概不信 —— 客户端传来的数字只能当提示，不能当依据。另外，提交接口要做频率限制和幂等处理，避免有人用脚本把请求刷成真正的「一百万次」。
