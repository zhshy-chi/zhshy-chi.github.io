Bugku ' or 1=1：第一句注入

2026-10-25 · 约 9 分钟 · Bugku CTF

这大概是所有人的第一句 SQL 注入。它教的其实不是那串 payload，而是「你输入的东西，是怎么一步步变成 SQL 语句的」。

题目信息

平台Bugku CTF
类型Web / SQL 注入
知识点字符型注入、注释符、order by、union

登录框背后发生了什么

页面是一个再普通不过的登录框：用户名、密码、登录按钮。抓包看，POST 到 check.php，两个字段。这类题的后端代码几乎可以背下来：

SELECT * FROM users WHERE name = '$u' AND pass = '$p';

关键在于是字符串拼接，不是参数化。$u 和 $p 被原样塞进 SQL 文本，数据库再去解析它。也就是说，我们输入的内容有机会「跳出引号」，变成语句结构的一部分。这就是注入的本质：代码和数据没有分开，而数据库并不认识哪一段是用户写的。

还有一点值得注意：后端通常不比对密码明文，而是执行查询后看结果集是否非空（num_rows 大于 0），非空就发会话、跳后台。所以只要能造出一行结果，密码是什么并不重要 —— 这题的漏洞不在密码校验逻辑，而在 SQL 语句的构造方式。

为什么 ' or 1=1 # 能进去

把 $u 换成 ' or 1=1 #，$p 随便填，拼出来的句子是：

SELECT * FROM users WHERE name = '' or 1=1 #' AND pass = 'x';

逐段读一遍：第一个单引号闭合了原来 name 的引号；or 1=1 让 WHERE 条件恒为真；# 把后面包括密码判断在内的所有内容注释掉。查询于是变成「选出所有用户」，后端只要判断结果集非空就认为登录成功 —— 密码从头到尾没参与判断。

这里有个容易被忽略的点：为什么注 name 而不是 pass？因为 name 在前面，一个注释符就能顺手干掉后面的密码条件。如果只注 pass，还要先处理前面那个引号，反而绕。

注释符：# 与 -- 的差别

MySQL 里 # 是行注释，-- 也是，但 -- 后面必须跟一个空格（或控制字符），否则不会被当成注释。这一点在手工注入时特别坑：写 -- 不带空格，整条语句语法错误，页面报错，你会误以为注入点不存在。另外 URL 里的 # 会被浏览器当成锚点，必须编码成 %23。

' or 1=1 %23
' or 1=1 --

两种写法等价。我后来固定用 %23，因为它不会因为末尾空格被浏览器或代理吞掉而出错。

用 order by 和 union 继续往下问

能登录只是开始。既然能控制查询，就能让它回显别的东西。第一步确定原查询有几个字段：

' order by 1 %23
' order by 2 %23
' order by 3 %23

第三条报错，说明原查询是两个字段。第二步用 union select 找回显位，union 要求两边列数一致，所以写成 union select 1,2：

' union select 1,2 %23

页面会把 1 和 2 显示在原来显示用户名、密码的位置，这两个位置就是回显位。之后把想查的函数塞进去就行，比如 union select database(),user()，再往下就能查表名、列名、拿账号。

这一步也解释了 union 的两个硬性条件：列数相同，且对应列的类型能兼容。所以常见写法是把数字填在字符串列的位置上 —— 数字在 MySQL 里会被隐式转换，不容易报错，回显也干净。

踩坑与复盘

  • 最初用 admin' or '1'='1，引号配对很容易数错，后来统一成 ' or 1=1 #；
  • URL 里的 # 没编码，整段 payload 被当成锚点截断，白试了好几次；
  • 字段数猜错时页面直接空白，别急着换 payload，先怀疑列数；
  • 登录成功后别停，回显位才是这题真正的入口。

参数化查询为什么能根治

因为它把 SQL 文本和参数分成两条路走：数据库先编译好语句模板（? 占位），再把用户输入当作「纯数据」填进去。输入的 ' 不再是语法符号，只是一个普通字符，靠闭合引号改变句式这条路从根上不成立。这也是现代框架的 ORM 基本不再手写拼接的原因。

防守方还有几层可加：数据库账号最小权限、关掉详细报错（别把 SQL 报错回显给用户）、登录失败统一提示。真正拦住注入的不是「过滤关键字」—— 黑名单永远漏，而是让数据没有机会变成代码。
