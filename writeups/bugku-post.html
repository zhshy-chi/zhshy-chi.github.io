Bugku web 基础 POST：看不见的参数

2026-09-26 · 约 6 分钟 · Bugku 练习场

这次参数不在 URL 里，地址栏怎么改都没用 —— 得从请求体里塞进去。

题目信息

平台Bugku 练习场
类型Web · POST 传参
知识点请求体、curl -d、Burp Suite Repeater

这是 GET 那题的姊妹题，题面几乎一样，只是把 $_GET 换成了 $_POST。它就一个目的：让你亲手感受一下「参数不在 URL 里」是什么感觉。

现象：地址栏怎么改都没反应

题面和上一题一样，也是要 what 等于 flag，但源码换成了 $_POST['what']。我按上一题的习惯在地址栏加 ?what=flag，页面毫无变化，回显是空的。

原因很直接：$_POST 只从请求体里取值，URL 上的 query string 它根本不看。地址栏能改的只有 URL，改不出一个请求体来，所以这条路从一开始就是死的。这个「空回显」其实是个很好的信号——它说明参数根本没送达，不是值不对。

参数在请求体里

一个 HTTP 请求分三部分：请求行（方法 + 路径 + 版本）、请求头、请求体。GET 一般没有请求体，参数在请求行的 URL 里；POST 的参数在请求体里，通常还配一个 Content-Type: application/x-www-form-urlencoded，body 长这样：

what=flag

多个参数就用 & 连起来：what=flag&submit=1。服务端的 $_POST 就是把这个 body 按同样的规则拆开。所以这题需要的操作不是「改地址」，而是「构造一个带 body 的请求」。地址栏做不到，浏览器插件、curl、Burp 都能做到。

用 curl -d 把参数塞进 body

curl 的 -d 就是干这个的：

curl -s -X POST -d "what=flag" http://靶机地址/
curl -s -i -d "what=flag" http://靶机地址/          # 顺便看响应头
curl -s --data-urlencode "what=flag" http://靶机地址/   # 参数含特殊字符时用这个

-d 会自动把方法设成 POST，也会补上 Content-Type: application/x-www-form-urlencoded，所以 -X POST 其实可以省。浏览器里也可以用 Hackbar 这类插件，它本质上是帮你拼一个 POST 请求；或者直接开 Console 写 fetch：

fetch('http://靶机地址/', {
  method: 'POST',
  headers: {'Content-Type': 'application/x-www-form-urlencoded'},
  body: 'what=flag'
}).then(r => r.text()).then(console.log)

Burp 抓包，扔进 Repeater

真实一点的流程是用 Burp。先把浏览器代理指向 127.0.0.1:8080，打开拦截，然后在页面上正常提交一次表单，你会看到这样一个请求：

POST / HTTP/1.1
Host: 靶机地址
User-Agent: Mozilla/5.0 ...
Content-Type: application/x-www-form-urlencoded
Content-Length: 9

what=abc

把 body 改成 what=flag，注意 Content-Length 要跟着变（Burp 会自动更新，手写的时候别忘了）。然后右键 Send to Repeater，在 Repeater 里点 Send，右边就能看到响应里的 flag{...}。Repeater 的好处是可以反复改、反复发，不用每次回浏览器点一遍。

抓不到包先检查三件事：浏览器代理有没有开、Burp 的 Intercept 是不是处于 on、目标是不是 HTTPS——HTTPS 要在浏览器里信任 Burp 的证书，否则请求会直接失败。

对比：请求行和 body

把 GET 和 POST 的原始请求摆在一起看，差别一目了然。GET 的第一行是 GET /?what=flag HTTP/1.1，参数在 URL 里，后面没有 body；POST 的第一行是 POST / HTTP/1.1，路径干干净净，参数在空行之后的 body 里。这就是为什么抓包工具里 GET 一眼就能看到参数，而 POST 要往下拉一点。

在 Repeater 里我顺手做了个对照实验：把同一个参数改成用 GET 发，页面立刻变回空回显。这反过来验证了服务端确实只读 $_POST。改一个变量、看一次结果，比盯着代码猜有效得多。

顺带说一个常见误解：POST 不会让参数「更安全」。body 只是不显示在地址栏，抓包照样看得一清二楚，明文 HTTP 下没有任何保密性可言。真正的保密靠 HTTPS，真正的可信靠服务端校验。

服务器不关心是谁发的

做完这题我记住一句话：服务器不关心请求是谁发的，只关心参数对不对。它看到的只有方法、路径、头、body，看不到你是用浏览器、curl 还是 Burp。User-Agent 可以伪装，Referer 可以伪造，所谓「只能用页面提交」从来不是限制。

防御侧：不要用「参数在 POST 里」当作安全措施；对 POST 接口同样做参数校验；涉及状态变更的接口要加 CSRF 防护，因为浏览器会自动带上 Cookie，而这恰恰是「谁发的」唯一还有点意义的地方。

复盘一条：GET 题做多了会形成「拼 URL」的肌肉记忆，遇到 POST 就容易卡住。后来我判断方法很简单——看地址栏里有没有参数，看表单的 method 属性，两个都对不上就默认去抓包。慢一点，但不会在错误的方向上耗时间。
