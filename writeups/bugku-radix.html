Crypto 进制 编码转换

Bugku 进制转换：先判断它是什么进制

2026-11-06 · 约 7 分钟 · Bugku CTF

一串看不懂的字符，先别猜，先数它的字符集。进制判断对了，转换只是一行代码的事；判断错了，怎么试都是乱码。

题目信息

平台Bugku CTF
类型Crypto（编码转换）
知识点二进制、八进制、十六进制、ASCII、Python int
flagflag{...}

题目给的是一长串数字，没有空格，也没有提示。新手最容易犯的错误是「先猜一个进制试一下」，猜错了再换一个，来回折腾。其实判断进制不需要灵感，只需要数一数：它用了哪些字符，最大的是几。

第一步：数它的字符集

拿出题目里的字符串，只看它出现过哪些字符，答案基本就出来了。只有 0 和 1，那必然是二进制；出现 2 到 7 但没有任何一位超过 7，是八进制；出现 8 或 9，就不是八进制；再出现 a 到 f，那大概是十六进制。这个方法不需要任何工具，用眼睛扫一遍就行。

还有一种情况：字符全在 0 到 9 之间，但每两位一组、数值都不超过 255，那它很可能是十进制的 ASCII 码，而不是某个大整数。这时候要看「分组」而不是看「进制」——长度是 3 的倍数、三位一组，往往就是十进制 ASCII。

一眼识别法：前缀与字符集

如果字符串带前缀，事情就简单了：0b 开头是二进制，0o 开头是八进制，0x 开头是十六进制。没有前缀时，按字符集和长度判断：

进制字符集典型样子
二进制0 101100110 01101100
八进制0 到 7146 154 141 147
十进制0 到 9102 108 97 103
十六进制0 到 9、a 到 f66 6c 61 67

注意一个细节：有 8 或 9 只能排除八进制，不能直接确定是十进制——十六进制也有 8 和 9。还要再看有没有 a 到 f。同理，只出现 0 到 7 时，八进制和十进制都可能，这时看有没有前导零、看数值分布。

用 int(x, base) 批量转换

Python 的 int() 第二个参数就是进制，这是整道题最核心的一行。把字符串按分隔符切开，逐个调用，就能把「看起来像数字的东西」变成真正的数值。

s = '01100110 01101100 01100001 01100111'
nums = [int(b, 2) for b in s.split()]
print(nums)                      # [102, 108, 97, 103]

# 八进制、十六进制同理，只换第二个参数
print(int('146', 8), int('66', 16))     # 102 102

如果字符串是连续的一整串、没有空格，就先按位宽切：二进制每 8 位、十六进制每 2 位、八进制每 3 位。用切片加 range 写循环最直观，比手动数位置靠谱。

s = '01100110011011000110000101100111'
nums = [int(s[i:i+8], 2) for i in range(0, len(s), 8)]
print(nums)      # [102, 108, 97, 103]

反过来，bin()、oct()、hex() 可以把整数转成带前缀的字符串，写脚本验证时很方便：hex(102) 得到 0x66。

再套一层 ASCII

进制转换本身只得到数字，还不是明文。102、108、97、103 看起来平平无奇，但把它们当 ASCII 码查表，就是 f、l、a、g。这一步用 chr() 完成，反向用 ord()。

print(''.join(chr(n) for n in [102, 108, 97, 103]))   # flag
print([ord(c) for c in 'flag'])                        # [102, 108, 97, 103]

很多题会在这里设一个坑：给出的数字范围不是 32 到 126，而是更大，比如四位数。那它可能不是 ASCII，而是 Unicode 码点，或者需要先做异或、加减某个固定值。遇到范围不对时，先别硬转，把最大值和最小值打印出来看看，往往能反推出规律。

前缀与常见坑

  • 前导零：0102 在 Python 3 里直接写是语法错误，放进 int() 则按十进制处理；别被「0 开头就是八进制」的旧习惯误导。
  • 大小写：十六进制的 A 和 a 等价，但有些老脚本只认一种，统一 lower() 最稳。
  • 缺位：二进制串长度不是 8 的倍数、十六进制串长度是奇数，说明要么有字符被吞了，要么开头少补了零。
  • 分隔符：空格、逗号、换行都可能出现，切之前先确认到底用的是哪个。

这几条里我踩得最多的是缺位。有次二进制串长 71 位，怎么切都对不上，最后发现是从网页复制时首字符的 0 被吞了，补一个零立刻正常。所以转换结果出现乱码时，先怀疑「长度」，再怀疑「进制」。

踩坑与复盘

这题我前后试了三次。第一次按十进制转，得到一堆不可见字符；第二次按十六进制转，像是对了但结果是乱码；第三次坐下来数了一遍字符集，发现只有 0 和 1，才意识到它是二进制。三次尝试里，前两次的失败都不是代码写错，而是判断错了前提。

教训很直白：先判断它是什么，再决定怎么处理。判断方法要能说清楚——「因为只出现了 0 和 1，所以是二进制」，而不是「感觉像二进制」。前者可以复现，后者只能靠运气。

引申：套娃编码

CTF 里更常见的是套娃：一层 base64，解出来是一串十六进制，转成字节又是一段二进制，最后才拼出 flag。处理这种题的诀窍是「一次只剥一层，每剥一层就看一眼输出可不可打印」。如果输出里大部分是可见字符，说明方向对了；如果全是乱码，说明这一层还没解完，或者解错了。

把流程写成脚本会比在线工具可靠得多，也便于回头检查。真正的收获不是这道题的答案，而是那套「判断、转换、验证」的循环——以后遇到任何一串看不懂的字符，你都知道第一步该做什么。
