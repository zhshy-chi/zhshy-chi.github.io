Web 正则绕过 preg_match

Bugku 数字验证正则绕过：preg_match 也有边界

2026-10-20 · 约 8 分钟 · Bugku CTF

题目用正则判断「你必须是纯数字」，而 PHP 的正则，恰好有几个经典边界。这篇把它们一次讲透。

题目信息

平台Bugku CTF · Web
类型正则校验绕过
知识点PCRE 的 $ 语义、数组传参、数字字符串
目标让「不是纯数字」的输入通过 ^\d+$

题面：必须是纯数字

页面提示很直白：输入必须全部是数字。提交 abc 会被打回，提交 123 能过第一关，但还不是最终答案。 源码大意如下 —— 先用正则卡一遍，再拿值去和一个目标数字比较，两边都过才给 flag： 

<?php
$num = $_GET['num'] ?? '';

if (!preg_match('/^\d+$/', $num)) {
    die('必须是纯数字');
}

if ($num == 2026) {          // 目标值，比赛里通常是别的数
    echo 'flag{...}';
} else {
    echo '数字对了，但不是那个数字';
}

看起来没什么问题：^\d+$ 只允许数字，== 再做一次值比较。但这两步各自都有边界，而它们叠在一起时，边界会互相放大。

边界一：$ 允许末尾有换行

这是 PCRE 最容易被忘掉的行为：默认模式下，$ 不只匹配「字符串结尾」，还匹配「结尾换行符之前」的位置。 所以 "2026\n" 能通过 /^\d+$/，尽管它明显不是「纯数字」。 

# 传 2026 后面跟一个换行（%0a）
curl "http://靶机/?num=2026%0a"

为什么这样还能过第二关？因为 PHP 比较时会把「数字字符串」解释成数字，而数字字符串允许尾随空白："2026\n" == 2026 成立。 两步都过了，但传进去的字符串根本不是我以为的那个「纯数字」。这也是 \z（绝对结尾）和 D 修饰符存在的原因： /^\d+$/D 或 /^\d+\z/ 才是真的「一直到结尾」。

同样的坑还有 %0d%0a、末尾空格 %20，以及忘了加 m 修饰符导致多行输入被整体匹配的情况。

边界二：传数组让 preg_match 返回 false

PHP 的参数天生可以是数组。?num[]=1 传进去，$_GET['num'] 就是一个 array，而 preg_match 的第二个参数要求字符串。 在 PHP 7 及更早的版本里，它会告警并返回 false；很多题的环境正好是这些老版本，于是校验就这样被「跳过」了。 

<?php
// 传 num[]=1 时，preg_match 收到的是数组
var_dump(preg_match('/^\d+$/', $_GET['num']));   // bool(false)
// 接着 $num == 2026 走的是数组和整数的比较，结果取决于后续代码

注意版本差异：PHP 8 对内部函数的字符串参数会直接抛 TypeError，所以这招在新环境里不一定成立。 比赛里我会先看响应是「空白 + 500」还是「正常报错」，判断它跑的是哪一代 PHP，再决定用哪条路。

还有一个常被忽略的点：preg_match 的返回值有三种 —— 1（匹配）、0（不匹配）、false（出错）。 很多代码只写 if (preg_match(...))，出错时返回 false 正好被当成「不匹配」；写成 if (preg_match(...) !== false) 才算认真检查。 可惜前一种写法实在太常见了。

边界三：数字的「等价写法」

就算正则写得严，只要后面还做类型转换，就有第二套语义。PHP 里这些值的身份常和看起来不一样：

  • "1e3"：is_numeric 认为它是数字（1000），但 \d+ 不认它，intval 却只取到 1。
  • "0x1A"：PHP 7 起不再当作十六进制数字，is_numeric 返回 false，但 intval("0x1A", 0) 又是 26。
  • " 123" / "123 "：前后空格在数字字符串里被容忍，正则不带 D 时也照样放行。
  • "0e123"：字符串比较时是「科学计数法的 0」，和另一个 0e... 用 == 比会相等 —— md5 碰撞题的老朋友。

这几种写法说明一件事：正则匹配的是「文本长得像什么」，不是「这个值是什么」。同一个输入，在正则眼里是字符串，在 == 眼里是数字，在 intval 眼里又变成另一个数。

为什么「过滤」不等于「校验」

过滤的思路是「把危险的东西去掉」，校验是「只接受我认识的东西」。前者永远在列举，后者可以收敛。这题的正则已经算白名单了（只允许数字），但它白名单的是字符，不是「数字这个类型」，于是换行、数组、等价写法都能钻进来。

真正的校验应该一步到位：用 filter_var($num, FILTER_VALIDATE_INT) 拿到整数，再做业务比较，而不是先看字符串长得像不像数字。

顺带记一个 filter_var 的坑：FILTER_VALIDATE_INT 默认拒绝前导零（"0123" 直接返回 false），也不接受 "1e3" 这种科学计数法， 想放宽得自己加 flag。所以「换 filter_var 就安全」也不完全对，关键还是先想清楚「合法输入到底是什么形状」。

防御建议

  • 正则加 D 修饰符或用 \z 收尾，避免 $ 放行末尾换行。
  • 入口先做类型检查：is_string / is_int，别让数组流进字符串函数。
  • 数字一律用 filter_var 加 FILTER_VALIDATE_INT，拿到 int 后再比较。
  • 比较用 ===，避免 == 的类型 juggling；哈希比较用 hash_equals。
