Web SQL注入 union information_schema

Bugku 成绩单：union 注入把别人的分数读出来

2026-10-27 · 约 10 分钟 · Bugku CTF

页面只有一个查询框，返回一张成绩表。既然我能控制这条查询，就能让它查我本来不该看到的东西 —— 这次的目标是整张 admin 表。

题目信息

平台Bugku CTF
类型Web / union 注入
知识点数字型判断、order by、union select、information_schema

只有一个查询框

页面中间一个输入框，输入学号，返回一张成绩表：姓名、学号、分数。没有登录，没有 cookie，请求是 GET，参数长这样：?id=1。先试 id=1、id=2 都能出结果，说明数据是按参数查的；再试 id=1' 直接报错，说明单引号被带进了 SQL —— 有戏。

我习惯先不急着上 payload，而是把「正常请求长什么样」记下来：响应里表格有几列、报错页长什么样。后面判断真假的时候，全靠这两个基线。

顺带记一下响应长度：正常页大概几 KB，空结果明显更短。有些差异肉眼看不出来，但在 Burp 的 Length 列里一眼就能看到，这比盯着页面猜要可靠得多。

先判断注入类型

数字型和字符型的区别在于有没有引号包裹。数字型可以直接接 and，字符型得先闭合引号。用两个恒真/恒假的表达式试：

?id=1 and 1=1
?id=1 and 1=2

前者正常返回、后者返回空表，说明 and 生效，是数字型（没有引号挡着）。如果是字符型，1 and 1=1 会整体被当成字符串，得写成 1' and '1'='1 才对。

order by 确定字段数

成绩表看起来是 3 列，但页面显示的列不等于查询里的列 —— 后端可能查了 5 个字段只显示 3 个。用 order by 二分：

?id=1 order by 3
?id=1 order by 4

第三条正常，第四条报 Unknown column，说明原查询是 3 个字段。这一步不能省，union 的列数必须和原查询严格一致，少一列多一列都会失败。

union select 找回显位

先用一个不存在的 id 让前半段查空，这样页面只会显示 union 后面的结果：

?id=-1 union select 1,2,3

1、2、3 分别出现在姓名、学号、分数三列里，三个位置都能回显。实际做题时未必要三个都用，挑一个不被截断的塞函数就行。

从 information_schema 摸表结构

MySQL 5.0 之后自带 information_schema，它是「关于数据库的数据库」：有哪些库、哪些表、哪些列全记在里面。先看当前库和版本：

?id=-1 union select 1,database(),version()

假设拿到库名 ctf、版本 5.7。接着查表名，用 group_concat 一次把多行拼成一行，省得翻页：

?id=-1 union select 1,2,group_concat(table_name)
from information_schema.tables where table_schema='ctf'

得到 users,score,admin 三张表。再查 admin 的列名：

?id=-1 union select 1,2,group_concat(column_name)
from information_schema.columns where table_name='admin'

如果表很多，group_concat 会被长度限制截断（默认 1024 字节），可以加 limit 0,10 分段取，或者用 substring_index 拆开。我第一次就只拿到半张表名，还以为是权限不够。

把要的字段拼到回显位

知道表名和列名之后，把真实数据查出来。用 0x3a（冒号）或 concat 拼接，一行里多带几个字段：

?id=-1 union select 1,2,group_concat(username,0x3a,password) from admin

分数列里就是一串 user:hash。密码是 MD5，拿去查一下或者按弱口令猜，最终拿到 flag{...}（真实内容已隐去）。完整链条其实就是四步：判类型 → 数字段 → union 找位 → 查元数据再查数据。

为什么 information_schema 是关键

没有它，注入只能靠猜表名和列名，效率低到不现实。它本质上是元数据：结构信息本身也是数据，一旦泄露，攻击者就不用猜了 —— 相当于把地图直接给了对方。所以生产环境里，业务账号通常只授予目标库的 SELECT 权限，读不到别的库；有的加固方案还会直接限制对它的访问。

复盘与防守方视角

  • 一开始 union select 1,2 少了列，页面空白，我以为是过滤，其实只是列数不对；
  • group_concat 有长度上限（默认 1024），表多的时候会截断，可以配合 limit 分段；
  • 查列名时忘了加 table_schema，结果从别的库里翻出一堆同名表。

防守上：参数化查询是根，最小权限是止损，关掉报错详情是隐藏线索。另外这张成绩单本来就不该由前端决定「查谁」—— 应该从会话里取当前用户，而不是接受一个 id 参数。很多越权就是这样和注入叠在一起出现的。

整题做完我只用了浏览器和 Burp，没上 sqlmap。不是说工具不好，而是手工走一遍才知道每一步为什么成立 —— 脚本能替你跑，但不能替你判断字段数和回显位。
