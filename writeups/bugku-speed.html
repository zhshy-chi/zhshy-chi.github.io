Web 时间窗口 base64

Bugku 速度要快：抢在倒计时之前提交

2026-10-24 · 约 8 分钟 · Bugku CTF

页面让我「快一点」，可我每次都慢了一步。后来才发现它只是把答案放在响应里，等我去解码、再立刻发回去 —— 手速根本不是解法，脚本才是。

题目信息

平台Bugku CTF
类型Web
知识点时间窗口、base64、脚本自动化

现象：每次都提示慢了一步

页面很朴素，一个输入框、一个提交按钮，旁边一行小字写着「要快」。我先按 F12 看源码，没有前端校验，也没有藏起来的隐藏字段。随手填了一个值提交，回显是「再快一点」；再提交一次，还是「再快一点」。一开始我以为是自己打字慢，后来干脆先把值在输入框里打好，眼睛盯着按钮，回显出来的一瞬间就敲回车 —— 结果依旧一样。

这时候我意识到方向错了。如果真的是拼手速，那这题对网络延迟太不公平，出题人不会这样设计。它大概率想要的是一个「自动」的流程：程序收到响应，立刻发下一条，中间不经过人。

为了确认这个猜测，我做了一次对照实验：把同一个请求用 curl 连发两次，对比响应里那段 base64。两次的内容完全不同，但解码后的格式和长度一样 —— 说明它是服务端每次现生成的，不是固定答案。这也解释了为什么手工复制永远赶不上：我复制的是上一次的答案，等我粘回去，窗口早就关了。

在响应里找到答案

打开 Burp，挂上代理，重新提交一次。请求本身没什么特别，一个普通 POST，参数只有一个。但响应体里除了那句「再快一点」，还多了一段奇怪的字符串：

ZmxhZ3suLi59

字符集是大小写字母加数字，长度还是 4 的倍数，还能正常解码 —— 典型的 base64。丢进 CyberChef，或者命令行解一下：

echo 'ZmxhZ3suLi59' | base64 -d

解出来是一行 flag{...}（真实内容已隐去）。但把解码结果直接粘贴回输入框提交，回显依然是「太慢」。这说明服务器不是让我去「读」这个值，而是让我在极短的时间内把它「还」回去 —— 而且每次请求给的值都不一样，人工复制粘贴必然超时。

让脚本替手速

思路变得很清楚：保持会话，发第一次请求，从响应里抠出 base64，解码，立刻作为参数发第二次请求，全程不经过人。用 requests.Session 保持 cookie，用正则抓那段字符串：

import base64, re, requests

URL = "http://靶机地址/index.php"
s = requests.Session()

r = s.post(URL, data={"a": "1"}, timeout=5)
m = re.search(r"[A-Za-z0-9+/=]{8,}", r.text)
answer = base64.b64decode(m.group(0)).decode()

r2 = s.post(URL, data={"a": answer}, timeout=5)
print(r2.text)

第一次跑还是「太慢」。原因不是脚本慢，而是我把提交的参数名猜错了 —— 两次请求的字段名必须和表单一致。从第一次请求里把键抄过来，改对之后再跑，屏幕上一行 flag{...}。

这里有个细节：必须用 Session，而不是两次独立的请求。服务端要靠 cookie 认出「你就是刚才那个请求的人」，换了会话，答案就对不上了。至于「人在回路」的环节 —— 解码、拼参数、发请求 —— 只要还留一个手工步骤，就一定会超时。

踩坑与复盘

  • 一开始想从前端 JS 里找「计时的逻辑」，但计时是服务端做的，前端只能看到结果；
  • 把 base64 解出来的东西当成最终答案，其实它只是「下一次请求的输入」；
  • requests 里 data 的键写死很容易错，最好直接从抓到的请求里复制；
  • 脚本里加日志会把窗口期吃掉，调试时先打印再删。

这类题到底在考什么

它不是手速题，是「能不能把人的动作变成程序」的题。真实的漏洞利用里，很多东西都需要在窗口期内完成：一次性 token、短时效的签名、要跑上百次请求才能出结果的盲注。手点是不现实的，脚本才是标准工具。做完这题之后我养成了一个习惯：凡是「要快」的页面，先看响应里有没有下一次的输入，再看能不能用脚本闭环。

顺便一提，如果目标有频率限制，脚本里记得加 sleep。练习环境也一样，别把人家的服务打挂 —— 这是最基本的礼貌。
