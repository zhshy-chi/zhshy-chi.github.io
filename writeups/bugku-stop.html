Bugku 你必须让他停下：让请求批量地跑

2026-10-07 · 约 8 分钟 · Bugku

页面会无限跳转，手动点不到终点。这类题的关键不是「点得快」，而是「发得多」 —— 把同一个请求重复到某一次命中条件为止。

题目信息

平台Bugku CTF 练习平台
类型Web / 逻辑与并发
知识点重定向循环、请求重放、竞态条件
工具Burp Intruder、Python requests

现象：停不下来的跳转

点开题目，页面几乎立刻开始自己跳。地址栏闪一下，又回到同一个页面，内容没变，标题也没变。按住 Esc 能停一瞬，但只要窗口还活着，下一秒它又跳走了。题目名字直白得可爱：「你必须让他停下」。

抓包看一眼就明白了：请求 /，服务端返回 302 Found，Location 指回 / 自己。也就是说，服务端在让浏览器自己追自己。如果响应里再夹一段 meta refresh 或者 location.href，那连 302 都省了，纯前端就能绕成死循环。

为什么点得快没用

一开始我也试过手动狂点、疯狂刷新，除了把浏览器卡住什么也没得到。原因很直接：重定向是服务端逻辑，你点得再快，也只是让同一个请求多跑了几趟，并没有改变任何参数。而且浏览器的跳转有节流，你根本快不过脚本。

换个角度想，如果这道题有解，那么解一定藏在「多次请求之间的差异」里。要么服务端维护了一个计数器，请求到第 N 次才放行；要么它有个时间窗口，某个瞬间条件成立；要么并发时两个请求同时读到了旧状态，产生了竞态。这三种情况共同点是：单次请求看不出异常，重复请求才可能撞上那一次例外。

用 Python 循环发 100 次

最直接的办法是写个脚本，把同一个 GET 重复发，并且关掉自动跟随跳转 —— 否则 requests 会跟着 302 一路跑到超时，你连原始响应都看不到。 

import requests

url = "http://靶机地址/"
s = requests.Session()

for i in range(100):
    r = s.get(url, allow_redirects=False, timeout=5)
    # 正常情况都是 302 跳回自己，某一次会不一样
    if r.status_code != 302 or "flag" in r.text:
        print("hit at", i, r.status_code)
        print(r.headers)
        print(r.text)
        break

Session() 的作用是复用 Cookie，很多计数型题目把状态放在会话里，用 requests.get 每次新建连接反而永远轮不到那一次。如果跑完 100 次都没有命中，就把次数调大，或者加个 time.sleep(0.1) 放慢节奏，看看是不是跟时间有关。

用 Burp Intruder 批量重放

不想写代码就用 Burp。把请求发到 Intruder，攻击类型选 Sniper，在任意位置加一个 payload 标记（哪怕这个参数根本没用），Payloads 里选 Numbers，从 1 到 100，步长 1。Start attack 之后会得到 100 条响应，重点看三列：状态码、Length、以及响应时间。

命中那一条通常很显眼：别人都是 302、长度几百字节，它突然变成 200，长度多出一大截；或者状态码不变但 Length 不一样。点开看看 Response，flag 就在里面。Intruder 社区版有速率限制，100 条会跑一会儿，正好用来观察规律。

找到那一次不一样的响应

我这次是在第 37 次左右命中的，响应从 302 变成了 200，body 里直接给了 flag。回头看响应头，还多了一个 X-Attempts: 37 之类的自定义头，等于把内部计数器写给你看了。也有题目会要求「并发」而不是「循环」：串行跑一百次永远不中，因为服务端每次都把状态重置，只有两个请求同时进来才会读到同一个旧值。

遇到这种情况就得上多线程。用 ThreadPoolExecutor 一次发十几个，或者用 Burp 的 Turbo Intruder 脚本，把 gate 打开后一次性放出所有请求。核心思路不变：制造「同时」，而不是「连续」。

先分清题目要的是「次数」还是「同时」。前者循环就够，后者必须并发 —— 方向错了，跑一千次也是白跑。

引申：重复提交与竞态

这类题在真实世界里对应的是竞态条件（race condition）。典型场景：优惠券只能领一张，但两个请求同时到达，都读到「未领取」，于是都写入了；余额只够扣一次，并发下扣成了负数；验证码只能用一次，两个请求同时校验通过。它们的共同点是「检查」和「使用」之间存在时间差，中间的状态没有加锁。

测试时的思路和这道题一模一样：把关键请求抓下来，去掉前端的防重放参数，然后用并发工具同时发几十份，看服务端有没有出现多扣、多领、多次成功。区别只是靶场里目标是拿 flag，真实项目里目标是证明影响。

防御建议

涉及状态变更的接口要做幂等：用一次性 token、数据库唯一索引或者行锁，把「检查 + 写入」放进同一个事务里。计数类逻辑放在服务端，并且对同一会话的请求做限速。重定向不要形成自环，跳转目标要做白名单校验，避免被拿来做开放重定向或者跳转链。
