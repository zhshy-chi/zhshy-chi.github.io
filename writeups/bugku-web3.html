Web HTML 实体编码 弹窗

Bugku web3：关不掉的弹窗和一段实体编码

2026-09-27 · 约 6 分钟 · Bugku 练习场

页面疯狂弹窗，关一个开一个。正确做法不是和它较劲，而是把 JS 关掉看源码。

题目信息

平台Bugku 练习场
类型Web · 前端干扰
知识点alert 死循环、禁用 JavaScript、HTML 实体编码

这题是我印象最深的一道「非漏洞」题。它没有服务端逻辑，只有一个很烦人的前端脚本和一段编码过的手写字符串，考的是你会不会绕开干扰，而不是会不会攻击。

一打开就是弹窗地狱

点开链接，alert 一个接一个。关掉一个，下一个立刻弹出来，鼠标都快点不过来。看页面源码大概是这种结构：

while (true) {
  alert('...');
}
// 或者用定时器，隔几十毫秒弹一次
setInterval(function () { alert('...'); }, 50);

不管哪种写法，它都是死循环：你关掉的是弹窗，循环还在跑，下一轮马上又弹一个。而且 alert 会阻塞 JS 执行，在弹窗被点掉之前，页面上的其它脚本也动不了。

这类题的设计意图很明显——用弹窗占满注意力，让你没机会看页面本身。我第一次就是硬关了几十次，最后发现页面内容压根没加载出来，纯属浪费时间。后来才想明白，它不是在跟我比手速。

别关弹窗，先把 JS 关掉

正确做法是让 JS 根本不执行。Chrome 开发者工具有个命令菜单：Ctrl+Shift+P，输入 Disable JavaScript，回车。刷新页面，弹窗没了，页面底部的内容露出来。这个开关只对当前 DevTools 会话生效，关掉面板或重开浏览器就恢复。

另外两条路也很好用：地址栏输入 view-source:http://靶机地址/，直接看服务器返回的文本，JS 完全不参与；或者用命令行把响应存下来慢慢看。用 view-source 有个额外好处——你能确定看到的是服务器发来的原始内容，而不是被 JS 改过之后的 DOM。这题两种结果一样，但养成这个习惯能省掉很多「源码和 Elements 对不上」的困惑。

curl -s http://靶机地址/ > page.html
grep -o "&#x\?[0-9a-fA-F]\+;" page.html | head -n 20

底部那串 &#xxx;

页面底部挂着一长串形如 &#102;&#108;&#97;&#103; 的东西。这是 HTML 数字字符引用（numeric character reference），&# 后面跟一个十进制码点，浏览器渲染时会把它还原成对应的字符。&#102; 是 f，&#108; 是 l，&#97; 是 a，&#103; 是 g，拼起来正好是 flag 的开头。

除了十进制，还有十六进制写法 &#x66;；除了数字引用，还有 &lt;、&amp;、&quot; 这类命名实体。三种东西在浏览器眼里是一回事：都是用 ASCII 字符表示某一个字符。

这题把整串结果都编码了，大小写、花括号、下划线一个不落。数字引用本身是区分大小写的——&#70; 是大写 F，&#102; 是小写 f——所以解码之后必须逐位核对，不能想当然地按小写抄。

解码，然后逐位核对

解码最省事的办法是浏览器控制台。把底部那串文本复制过来，赋给一个变量，然后借 textarea 让浏览器自己解析实体：

var s = '&#102;&#108;&#97;&#103;...';
var d = document.createElement('textarea');
d.innerHTML = s;
console.log(d.value);

innerHTML 会让浏览器把实体解析掉，再读 value 就拿到明文。这里用 textarea 而不是直接 innerHTML 到页面上，是因为直接插进页面就等于自己给自己制造一个 XSS。

也可以用 Python 一行搞定，把那段编码粘贴进去：

python -c "import html,sys; print(html.unescape(sys.stdin.read()))"

解出来是 flag{...} 这一串。我抄进提交框之前又对着页面原文核了一遍大小写和花括号，确认没因为手抄漏字符——这题平台是严格匹配的，差一个字母都过不了。核对完提交，通过。

手抄编码串很容易出错，尤其是 l 和 1、0 和 O。更稳的做法是把解码结果直接重定向到文件，再用 Ctrl+F 搜 flag，减少中间环节。

实体编码在 XSS 里的影子

HTML 实体编码在 XSS 里是个常见的绕过点。很多 WAF 或过滤函数只匹配字面量的 script 标签，但浏览器解析 HTML 时会先把实体解码，所以源码里写成实体形式的内容，到了 DOM 里就是真正的标签。

举个例子：如果过滤把 < 拦了，却没拦 &#60;，那么 &#60;img src=x onerror=alert(1)&#62; 进入 HTML 后会被浏览器解码成一段真正的 img 标签，onerror 照样执行。绕过能成立的前提是：实体只在 HTML 解析上下文里被解码。写在 script 标签内部的字符串不会，那是 script data 状态，&#60; 在那里就只是几个普通字符。所以注入点落在正文、属性值、还是 JS 字符串里，三种情况的利用方式完全不同。

这题本身没有漏洞，但它让我第一次意识到「你看到的不等于浏览器解析后的」。这个差别在 XSS 里就是能不能打进去的差别，也是我后来做题时愿意多看一眼源码的原因。
